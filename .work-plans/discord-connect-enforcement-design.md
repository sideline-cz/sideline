# Discord Connect + Enforced Onboarding + Manual Role Sync — UX/UI Design Spec

**Bug:** "Nefunguje discord onboarding pres webapp" (35993506-…)
**Scope:** user-facing design only. No application code changed by this doc.
**Companion docs:** `.work-plans/discord-native-onboarding.md` (Discord-native
Welcome Screen / Server Guide — *different feature*, guild-side),
`.work-plans/discord-native-onboarding-design.md` (the `TeamSettingsPage`
Onboarding card). This spec deliberately does **not** touch either.

---

## 0. Which flow is which — my assumption, stated up front

The parallel architect thread is resolving the data model. This spec assumes the
following split, which I verified against the code. **If the architect concludes
otherwise, §2–§4 need re-reading; §5 (role sync) is independent and holds either
way.**

| | **Flow A — Team/guild onboarding** | **Flow B — Member Discord connect** |
|---|---|---|
| Who | Team captain / founder (one-off, once per team) | Every player, every time they join a team |
| Entry | `/onboarding/$token` (token minted by a global admin on `/admin/onboarding-tokens`), or `/create-team` | `/invite/$code` → sign in → join → **must land in the team's Discord guild** |
| Code | `applications/web/src/components/pages/OnboardingPage.tsx`, `routes/onboarding.$token.tsx`, steps `'identity' \| 'discord'` | `routes/invite.$code.tsx` → `setPendingDiscordJoin()` → `components/organisms/PendingDiscordJoinBanner.tsx` |
| "Connect Discord" means | *Invite the Sideline bot into my Discord server* (`discord.com/oauth2/authorize?...&scope=bot`) | *Join the team's Discord server* via a one-time `discord.gg/…` invite generated by the bot (`api.invite.getJoinStatus` → `discordInviteUrl`) |
| Already enforced? | **Yes, structurally.** `DiscordFormSchema.guildId` is required and is only set when `selectedGuild.botPresent` — the captain physically cannot submit step 2 without a bot-present guild. | **No.** Entirely optional and easy to miss. |

**Critical clarification that changes the whole design:** authentication in this
app *is* Discord OAuth (`HomePage.tsx` → `auth_signInDiscord`; every
`Auth.CurrentUser` carries a non-optional `discordId`). There is therefore **no
such thing as a Sideline user without a Discord account**, and "connect my
Discord account" is not an account-linking step. Flow B is purely *guild
membership*. This removes the "user has no Discord account" failure mode
entirely and materially lowers the risk of enforcing it — see §3.

The reporter's three asks map like this:

1. *"uzivatelum se link neukaze"* → **Flow B**, §1 + §2.
2. *"udelej pripojeni na discord vic enforced step"* → **Flow B**, §3.
   (Flow A also gets a small polish pass, §7 — it is a genuine but separate
   usability problem and should not block the bug fix.)
3. *"pri prihlaseni uzivatele na discord pridej role co ma mit + moznost manual
   syncu roli"* → **§5**.

## 1. Why the link is invisible today (UX root causes)

These are observable in the current code and each one independently loses the
link. The fix must close all of them, not just the first.

1. **The link lives only in `localStorage`.** `routes/invite.$code.tsx`
   `handleJoined` calls `setPendingDiscordJoin({ acceptanceId, teamId, ts })`.
   `PendingDiscordJoinBanner` reads it with `getPendingDiscordJoin`. Different
   device, different browser, private window, cleared storage, storage
   exception → **the user never sees the link again**, even though the server
   still holds a perfectly valid `invite_acceptances` row.
2. **The banner is not mounted on the page the user actually lands on.**
   `PendingDiscordJoinBanner` is rendered inside `AuthenticatedLayout`, which is
   only used by `routes/(authenticated)/teams/$teamId/route.tsx`. A brand-new
   member with an incomplete profile is sent to `/profile/complete`, which is a
   `(no-team)` route rendering its own standalone full-screen shell. **The most
   common first-join path shows the banner zero times.**
3. **One click and it is gone forever.** `handleOpen` calls
   `clearPendingDiscordJoin()` on click — before we have any evidence the user
   actually joined. Popup blocked, wrong Discord account in the browser, "this
   invite is invalid", user closes the tab → link destroyed.
4. **Dismiss is permanent.** The `X` calls `clearPendingDiscordJoin()` with no
   snooze/restore path and no re-entry point anywhere else in the product.
5. **24 h hard expiry.** `STALE_MS = 24h`. A user who joins on Friday evening
   and next opens the app on Monday gets nothing.
6. **It looks like chrome, not like a task.** A one-line strip above the sticky
   header, `bg-primary/10`, that scrolls away with the content. On a phone it is
   ~40 px of muted text competing with the breadcrumb bar. Banner blindness.
7. **`autoJoinTeams()` produces no acceptance at all.** The
   `/profile/complete` success path calls `api.auth.autoJoinTeams()`, whose
   `UserTeam` result carries no `acceptanceId`. Those members have no invite URL
   in the first place.

**Design consequence #1: the source of truth for "does this user still need to
join the guild, and what is their link" must move to the server** and be
readable at any time from any device. `localStorage` may remain only as a
*snooze* record (§3.4), never as the carrier of the link.

## 2. Where the Discord connect entry point lives (Flow B)

Four placements, ordered by how hard they are to miss. All four read the same
server-derived state (contract in §6), so they can never disagree.

### 2.1 The interstitial — `/teams/$teamId/connect-discord` *(primary)*

A real route, not a modal. Directly mirrors the existing
`/profile/complete` precedent, which is the app's established "mandatory step"
pattern (`routes/(authenticated)/teams/$teamId/index.tsx`, `my-payments.tsx`,
`create-team.tsx`, `(no-team)/profile/index.tsx` all
`throw redirect({ to: '/profile/complete' })` when `!isProfileComplete`).

Being a route rather than a `Dialog` is a deliberate a11y and robustness call:
no focus trap to get wrong, back button works, the URL is shareable to the
user's phone, and a crashed poll cannot leave an orphaned Radix overlay (see
`applications/web/AGENTS.md` § "Dialogs Must Be Always-Mounted").

Layout — reuse the `ProfileCompletePage` / `NoTeamPage` shell verbatim
(standalone `flex min-h-screen flex-col` + header with `app_name` +
`LanguageSwitcher`, `Card className='w-full max-w-md'`):

```
┌─────────────────────────────────────────────────┐
│              (  Discord glyph  )                │   size-12 rounded-full bg-primary/10
│                                                 │
│         Join the {teamName} Discord             │   CardTitle
│  Sideline runs on Discord. Events, RSVPs and    │   CardDescription
│  team chat all happen there.                    │
├─────────────────────────────────────────────────┤
│  [  Open Discord server        ↗  ]  (primary,  │   Button w-full, asChild <a target=_blank>
│                                       w-full)   │
│  discord.gg/aB3xY9q            [Copy]           │   selectable text + copy Button variant='ghost' size='icon'
│                                                 │
│  Already joined? We'll notice automatically.    │   text-xs text-muted-foreground
│                                                 │
│  [ Skip for now ]                               │   Button variant='ghost' — see §3.4
└─────────────────────────────────────────────────┘
```

Key detail for the reported bug: **the raw `discord.gg/…` URL is rendered as
selectable text with a copy button**, not hidden behind the button label. A
blocked popup, an in-app browser (Instagram/Messenger webview — very common for
a link a captain pasted into a group chat), or a desktop session where Discord
is installed on the phone all fail with a button-only design. Use
`copyToClipboard` from `~/lib/clipboard` per `AGENTS.md`.

The button does **not** clear any state. State only advances on server-observed
guild membership (§4.3).

### 2.2 Persistent dashboard card — `TeamDetailPage` *(the durable home)*

Slot a `DiscordConnectCard` organism as the **first child** of the dashboard
stack in `components/pages/TeamDetailPage.tsx`, above `StatCards` and above
`OutstandingPaymentsBanner`. It reuses the amber-alert card visual language
already established by `OutstandingPaymentsBanner` and the `AwaitingRsvp`
section in `TeamDetailPage` (`border-amber-200 bg-amber-50/50
dark:border-amber-800 dark:bg-amber-950/20 py-4 gap-3`, `size-6 rounded-full
bg-amber-100` icon chip, `CardTitle className='text-sm font-semibold'`).

**Not dismissible.** It disappears when, and only when, the server says the user
is in the guild. This is the answer to root cause #4 — there is always a way
back to the link.

```
┌─ amber card ────────────────────────────────────────────────┐
│ (!)  You're not in the team's Discord yet   [Join Discord ↗]│
│      Events and RSVPs are posted there.       discord.gg/…  │
└─────────────────────────────────────────────────────────────┘
```

Once connected, the same slot becomes a neutral (`default` Card) **"Discord"**
card carrying the role-sync affordance (§5.2) — so the card is a permanent,
predictable home for everything Discord, not a nag that vanishes.

### 2.3 Sidebar nav item — `AppSidebar`

Add to the first (personal) nav group, immediately under `sidebar_dashboard`:

| | |
|---|---|
| Icon | `MessageCircle` (lucide; the codebase has no brand Discord icon component — `HomePage.tsx` inlines an `<svg aria-label='Discord'>`. Extract that inline SVG into `components/atoms/DiscordIcon.tsx` and reuse it here so brand identity is consistent. Low cost, high recognisability.) |
| Label | `tr('discord_navTitle')` → "Discord" |
| To | `/teams/$teamId/connect-discord` |
| Badge | when not connected, a `<Badge variant='destructive' className='ml-auto size-2 rounded-full p-0'>` dot with `<span className='sr-only'>{tr('discord_navNeedsAttention')}</span>` |

Rationale: a nav item is the only placement that survives every banner-blindness
and dismissal failure mode, and it is where a user goes looking when someone in
the team chat says "the link is in the app".

### 2.4 Profile page — `MyProfilePage`

A read-only **"Discord" card** under the existing profile card showing
`@{user.username}`, the avatar already rendered there, and per-team connection
rows:

```
Discord
  @maxic                                   [avatar]
  ────────────────────────────────────────────────
  Ultimate Praha        ● Connected     [Sync roles]
  Juniors               ○ Not joined    [Join ↗]
```

This is the "I know I have a Discord problem, where do I look" destination. It
is global (no `teamId` in the URL), so it must list every team — consistent with
the `(no-team)` route group rules.

### 2.5 Out-of-app delivery (recommended, cheap)

Emit an in-app notification (`Notification.NotificationType` gains
`'discord_connect_pending'`) at invite-acceptance time, so the link is also
durable in `/teams/$teamId/notifications` and drives the existing bell badge.
Optional for v1; it costs one enum value and closes the "user only checks the
app once a week" gap. **Do not** put the one-time invite URL in a Discord DM —
by definition the user is not reachable there.

## 3. How "enforced" should work — recommendation

### 3.1 Recommendation: **soft gate**, not a hard gate, not a mere nag

Concretely: **a mandatory-looking, skippable interstitial + a non-dismissible
persistent card + a nav badge — with zero blocked functionality in v1**, and a
pre-designed escalation ladder (§3.5) we can climb per-team, later, behind a
flag.

Placement of the redirect, mirroring the `isProfileComplete` precedent exactly:
`throw redirect({ to: '/teams/$teamId/connect-discord' })` from
`routes/(authenticated)/teams/$teamId/index.tsx` **only** — the dashboard index.
Every other team route is reachable directly. This is what makes it a *step in a
flow* rather than a wall: the user's first landing after joining always goes
through it, but a deep link to an event, a payment, or the roster never does.

### 3.2 Why not a hard gate

This is a **production** app with existing members who are working fine today,
and the gate's input signal does not exist yet in the database. I checked:
there is no `in_guild` / `discord_joined_at` column on `team_members` or
`users`; the only guild-membership evidence is the transient bot
`GuildMemberAdd` → `Guild/RegisterMember` RPC path and the
`invite_acceptances.discord_code` row. So on day one of any gate, **the honest
answer for the entire existing user base is "unknown", not "not connected"**.

A hard gate on an unknown signal is a self-inflicted outage: every existing
member of every team is bounced to a "join Discord" wall, half of them are
*already* in the guild, they click a fresh invite for a server they are already
in, Discord says "you are already a member", and they are stuck in a loop with
no escape. That is a worse production incident than the bug being fixed.

Secondary reasons:

- Discord itself can refuse the join for reasons the user cannot fix: guild at
  the 500-member cap for a non-boosted invite, raised verification level
  requiring a verified phone number, the user is banned from the guild, or the
  bot lost `CREATE_INSTANT_INVITE`. A hard gate converts each of these into a
  permanent lockout with a support ticket.
- Captains are legitimately unreachable at 22:00 on a Sunday.
- A minority of adult players (and, notably, parents of junior players who hold
  the account) genuinely do not want to be in the Discord server but still need
  RSVP and payments. Blocking payments over a chat-server membership is a bad
  trade.

### 3.3 Why not a dismissible nag either

The reporter's complaint is precisely that the current thing is a dismissible
nag that vanishes. A dismissible banner is the status quo. The design must make
the state **irreversible-by-dismissal**: the persistent card and the nav badge
have no close button, ever.

### 3.4 "Skip for now" — the escape hatch, precisely specified

- Label: `tr('discord_connect_skip')` → "Skip for now" / "Přeskočit zatím".
  Never "Cancel", never "No thanks" — the copy must communicate deferral, not
  refusal.
- Clicking it navigates to `/teams/$teamId` (or `?next=` if present) and writes
  a **snooze**, not a dismissal.
- Snooze storage: `localStorage`, user-scoped per `AGENTS.md`
  § "User-Scoped `localStorage` Keys":
  `` const discordSnoozeKey = (userId: string, teamId: string) => `sideline:discord-connect-snoozed:${userId}:${teamId}`; ``
  Value = epoch ms. `try/catch` both `getItem`/`setItem`; on throw, treat as
  *snoozed* (the safe default — never trap a user in a redirect loop because
  Safari private mode threw).
- Snooze duration: **24 h for the first three skips, then 7 days**. The
  interstitial redirect is suppressed while snoozed; the persistent card and the
  nav badge are **not** suppressed, ever.
- Snooze suppresses the *redirect only*. Navigating to
  `/teams/$teamId/connect-discord` by hand always shows the page.
- Third and subsequent visits to the interstitial add a `Alert variant='warning'`
  above the CTA: `tr('discord_connect_nudgeRepeat')` → "You've skipped this a
  few times. Ask your captain if you're stuck — without Discord you'll miss
  event announcements." This is the escalation that a nag lacks and a hard gate
  overshoots.

### 3.5 The escalation ladder (designed now, shipped later)

Ship rung 1 only. Rungs 2–3 are behind a per-team switch
(`team_settings.discord_required`, default `false`) on `TeamSettingsPage`, so a
captain opts *in* to strictness for their own team and owns the support load.

| Rung | Behaviour | Ship when |
|---|---|---|
| **1 — soft gate** *(v1, this spec)* | Interstitial on dashboard index + non-dismissible card + nav badge. Nothing blocked. | Now |
| **2 — inline action prompt** | Actions whose *whole value* is Discord-side are blocked inline, in place, with the connect CTA rendered where the control was — never a modal, never a redirect. Exactly three: (a) the RSVP control in `EventRsvpPanel` for events with a Discord announcement, (b) "Create Discord channel" style captain actions, (c) roster channel access. Everything else (payments, profile, rules trainer, leaderboards) stays open. Copy: `tr('discord_connect_blockedAction')` → "Join the team's Discord to RSVP." + inline `Button size='sm'`. | After ≥2 weeks of rung 1 telemetry, per-team opt-in |
| **3 — captain-driven** | Captain sees an "N members not in Discord" list on `TeamMembersPage` with a bulk "Remind" action. Social pressure beats software gates for a sports team. | Any time; independent of 1–2 |

### 3.6 Rollout / migration plan for existing users — the load-bearing part

The connection state is **tri-state, and `unknown` renders nothing**:

| State | Meaning | Interstitial redirect | Persistent card | Nav badge |
|---|---|---|---|---|
| `connected` | Bot has confirmed this `discord_id` is in the team's guild | no | "Discord" neutral card (§5.2) | none |
| `not_connected` | Bot has confirmed the user is **absent** from the guild | yes (unless snoozed) | amber card | dot |
| `unknown` | We have not yet observed this user's guild membership | **no** | **none** | **none** |

Rollout sequence — each step is independently revertible:

1. **Ship read-only first.** Backfill `is_in_guild` from the bot: on `Ready`,
   paginate `GET /guilds/{id}/members` (or `GUILD_MEMBERS_CHUNK`) for every
   registered guild and mark every matched `users.discord_id` `connected`.
   Everyone else stays `unknown`. **No UI is enabled during this step.**
2. **Enable UI for `not_connected` only after backfill completion is confirmed
   per guild** (a `teams.guild_members_backfilled_at` timestamp, or the
   architect's equivalent). A team whose backfill has not completed shows
   `unknown` for all its members and therefore shows nothing. This is the single
   most important safeguard: **a guild we failed to read must never be
   interpreted as "nobody is connected"**.
3. **Dark-launch the interstitial redirect for new joiners only** for the first
   7 days: gate the redirect on `team_members.joined_at > <flag enabled at>`.
   The persistent card + nav badge go live for everyone immediately (they are
   informational and dismiss-proof but block nothing). Existing members thus get
   a visible, correct affordance without ever being bounced.
4. **Kill switch.** A single server-side flag that forces every user to
   `unknown` and instantly removes all three surfaces. Wire it before step 3.
5. **Never gate on a stale signal.** If the bot has been disconnected from a
   guild for > 15 min, that guild's members degrade to `unknown` rather than
   being reported `not_connected`. A bot outage must not manifest as an
   app-wide "you're not in Discord" false alarm.

**Explicit residual risk:** a user who is in the guild under a *different*
Discord account than the one they log into Sideline with will be permanently
`not_connected`. They will see a persistent amber card they cannot satisfy.
Mitigation: the interstitial's failure state (§4.4) offers "I'm already in the
server — this looks wrong" → `tr('discord_connect_wrongAccount')` explaining the
account mismatch, plus the "Skip for now" escape. Do **not** attempt automatic
account re-linking in v1.

## 4. States for the connect flow

### 4.1 Loading

Two distinct loading shapes; do not conflate them.

- **Route load** (resolving connection state + invite URL): the interstitial
  renders the full card shell with a `Skeleton` (`components/ui/skeleton`) for
  the button row and the URL row — `<Skeleton className='h-10 w-full' />` +
  `<Skeleton className='h-4 w-40' />`. Never a bare spinner on a blank page; the
  title and description are static and should paint immediately.
- **Invite generation in flight** (the acceptance row exists, the bot has not
  yet returned a code — the current `invite_preparingDiscordInviteDescription`
  case): the primary button renders `disabled` with
  `<Loader2 className='size-4 animate-spin' aria-hidden='true' />` and the label
  `tr('invite_preparingDiscordInviteTitle')` ("Preparing your Discord
  invite" / "Připravujeme pozvánku" — **existing key, reuse it**). The
  descriptive line below uses the existing
  `invite_preparingDiscordInviteDescription`. Poll every 2 s (matches the
  current banner) for at most 60 s, then fall to §4.4 `generation_failed`.

The card's status region is `<div role='status' aria-live='polite'>` so the
transition preparing → ready is announced once (§8).

### 4.2 Empty — no invite link available

Distinguish two genuinely different situations; the current banner collapses
them into one destructive strip.

**(a) No acceptance row at all** (the `autoJoinTeams` path, root cause #7, or an
acceptance older than the server's retention):

> **Title** `discord_connect_noLinkTitle` — "We need a fresh invite"
> **Body** `discord_connect_noLinkBody` — "Your invite link has expired. Generate a new one — it's instant."
> **Action** primary `Button` `discord_connect_regenerate` — "Get a new invite"

This is the single highest-value addition in this spec: **a self-service
"regenerate my invite" button**. It structurally removes the "user has no link
and no way to get one" class of bug, regardless of what caused the original
link to go missing. It requires a server endpoint (§6) but no new concepts.

**(b) The team has no Discord guild configured** (captain never finished Flow A):

> `discord_connect_noGuildTitle` — "This team isn't linked to Discord yet"
> `discord_connect_noGuildBody` — "Your captain still needs to connect a Discord server. Nothing for you to do here."

No CTA for a player. `variant='default'` Alert, muted tone. Crucially: in this
case the connection state is `unknown` for everyone, so **no card, no badge, no
redirect** — this copy is only ever reached by navigating to the route directly.

### 4.3 Success — "we noticed you joined"

After the user clicks through to Discord, the interstitial does **not**
navigate away and does **not** clear state (fixing root cause #3). It flips to a
waiting state and verifies:

- Poll connection state every 3 s for up to 3 min, plus an immediate refetch on
  `window.focus` (the same `window.addEventListener('focus', …)` idiom already
  used in `OnboardingPage`'s `GuildPicker` and documented in `AGENTS.md`
  § "`window.focus` → `router.invalidate()`").
- While waiting: `discord_connect_waiting` — "Waiting for you to join…
  This page will update by itself."
- On success: the card swaps to a `success` state —
  `<CheckCircle className='size-6 text-success' />`, title
  `discord_connect_successTitle` ("You're in!"), body
  `discord_connect_successBody` ("Welcome to the {teamName} Discord. We're
  setting up your roles."), and **automatically enqueues a role sync** (§5.4).
  A `toast.success` fires via the standard `run({ success })` mechanism, then
  auto-navigate to `/teams/$teamId` after 1.5 s (or immediately on click of
  `discord_connect_continue` → "Continue to the app").
- The success announcement goes through the same `role='status'` region so it is
  read out; the auto-navigate is long enough (1.5 s) not to yank focus mid
  announcement, and the explicit Continue button means a keyboard user is never
  dependent on the timer.

### 4.4 Failure

| Case | When | Copy key → English | UI |
|---|---|---|---|
| `generation_failed` | `JoinStatus.errorCode` is `Some` (any `InviteGeneratorErrorCode`) | reuse existing `invite_discordInviteFailedTitle` / `invite_discordInviteFailedDescription` | `Alert variant='destructive'` + `Button variant='outline'` "Try again" (`discord_connect_retry`) |
| `welcome_channel_missing` / `welcome_channel_deleted` | same enum, captain-fixable | `discord_connect_error_captainAction` — "Your captain needs to finish setting up the Discord server. We've told them." | `Alert variant='warning'`, no retry button (retrying cannot help), "Skip for now" is the only action |
| `bot_missing_perms` | bot lacks `CREATE_INSTANT_INVITE` | `discord_connect_error_botPerms` — "The Sideline bot can't create invites in this server. Ask your captain to re-add the bot." | `warning`, no retry |
| `rate_limited` | Discord 429 | `discord_connect_error_rateLimited` — "Discord is busy. We'll retry automatically in a moment." | inline muted text, auto-retry with backoff, no user action |
| `network_error` / `discord_error` / `unknown` | anything else | `discord_connect_error_generic` — "Something went wrong on Discord's side. Try again in a minute." | `destructive` + retry |
| `not_observed` | polled 3 min after the user opened the invite, still `not_connected` | `discord_connect_notSeenTitle` — "We haven't seen you in the server yet" / `discord_connect_notSeenBody` — "If you accepted the invite, it can take a minute. If Discord said the invite was invalid, get a new one." | two buttons: `discord_connect_regenerate` ("Get a new invite") and `discord_connect_skip` |
| `wrong_account` | user self-reports via the link in `not_observed` | `discord_connect_wrongAccount` — "Already in the server? You may be signed into Sideline with a different Discord account than the one you use in the server. Sign out and sign in with the right one." | `Alert variant='default'` + `Button variant='outline'` "Sign out" |

### 4.5 OAuth round-trip failure / cancellation

Three distinct round-trips exist; only two are OAuth, and they need different
treatment.

1. **Sign-in with Discord** (`getLogin()` → `window.location.href`). The user
   cancels at Discord's consent screen → Discord bounces back to the callback
   with `error=access_denied`. Today this lands on `/` with no explanation.
   Design: `routes/index.tsx` reads `?error` from the search params and renders
   an `Alert variant='destructive'` above the sign-in button:
   `auth_error_cancelledTitle` — "Sign-in cancelled" /
   `auth_error_cancelledBody` — "You didn't approve the Discord sign-in. Nothing
   was changed." with the sign-in button still present as the retry. Pending
   invite/onboarding tokens in `localStorage` (`setPendingInvite`,
   `setPendingOnboarding`) **must survive** so the retry resumes the same flow —
   they are only cleared on success.
2. **Re-auth for an expanded scope** (`JoinResult.requiresReauth` — already
   modelled and already handled by `InvitePage`'s `invite_reauthTitle` card).
   Keep it. Add the cancelled branch: returning to `/invite/$code` with
   `?error=access_denied` re-renders the same reauth card plus the destructive
   alert from (1), so the user is never dumped on a page with no context.
3. **Joining the guild** (`discord.gg/…`) — **not OAuth**, just a link. There is
   no callback and no error code. This is exactly why §4.3 uses observed
   membership rather than a return URL as the completion signal, and why the
   link is never cleared on click.

Flow A's bot-invite round-trip (`discord.com/oauth2/authorize?…&scope=bot`) is
also a real OAuth cancel case — covered in §7.

## 5. Manual role re-sync

### 5.1 The underlying gap (for the architect's benefit)

`applications/server/src/rpc/guild/index.ts` `registerMember` only calls
`setupNewMember(team, newMember, payload.roles)` when the membership is newly
created or reactivated. When the member **already exists and is active** — which
is exactly the webapp-invite ordering: join team in the app first, join Discord
second — it logs `Member … already active in team …` and returns without ever
pushing that member's Sideline roles into Discord. That is the "pri prihlaseni
uzivatele na discord pridej role co ma mit" half of the report. The UX below
assumes that automatic path gets fixed; the manual affordance is the safety net,
not the fix.

### 5.2 Member-facing placement

**Primary: the "Discord" card on `TeamDetailPage`** (the same slot as §2.2, in
its `connected` form). Neutral `Card`, not amber:

```
┌─ Discord ───────────────────────────────────────────────────┐
│ (D)  Discord                     ● Connected                │  Badge variant='success'
│      Roles synced 4 minutes ago            [ Sync roles ]   │  Button variant='outline' size='sm'
└─────────────────────────────────────────────────────────────┘
```

- Relative time via `useFormatDate().formatRelative(lastSyncedAt)` per
  `AGENTS.md` § Date Formatting — no hand-rolled "4 minutes ago".
- **Secondary: `MyProfilePage`** Discord card (§2.4), one `[Sync roles]` per
  team row. Same component, same states.
- **Not in the `NavUser` dropdown.** Role sync is team-scoped; the user menu is
  global and already carries profile / notifications / language / theme /
  versions. Adding a team-scoped action there is a category error and it would
  be the least discoverable placement of the three anyway.

**Copy:** `discord_syncRoles` → "Sync roles" / "Synchronizovat role".
Not "Re-sync" (jargon), not "Refresh" (ambiguous with page reload). The full
sentence lives in the tooltip / description: `discord_syncRolesHelp` →
"Re-applies your Sideline roles to the Discord server." /
"Znovu nastaví tvoje Sideline role na Discord serveru."

### 5.3 Admin-facing placement

- **Per member** — `PlayerDetailPage` (`/teams/$teamId/members/$memberId`), in
  the header of the existing `roles_currentRoles` card, as a
  `Button variant='ghost' size='sm'` with a `RefreshCw` icon, mirroring the
  `handleStartEditing` ghost button already in that card's header. Visible only
  with `role:manage`. Label: `discord_syncRolesFor` → "Sync Discord roles".
- **Bulk** — `TeamMembersPage` header, `Button variant='outline'`
  `discord_syncAllRoles` → "Sync all Discord roles". This fires a burst of
  Discord API calls across the whole roster, so it **must** be confirmed through
  an `AlertDialog` per `AGENTS.md` § "Confirm Before Destructive Actions"
  (it is not destructive, but it is a bulk irreversible-from-the-UI side effect
  and the same rule applies):
  - Title `discord_syncAllConfirmTitle` — "Sync roles for all members?"
  - Description `discord_syncAllConfirmBody` — "This re-applies Sideline roles to {count} members in Discord. It can take a few minutes."
  - Confirm `discord_syncAllConfirm` — "Sync all" / Cancel `discord_syncAllCancel` — "Cancel"
- **Not** on `RolesListPage` — that page edits role definitions, not membership.

### 5.4 States and feedback

The button is a small state machine. All four states occupy the same box so the
layout never jumps (fixed `min-w` on the button).

| State | Button | Adjacent text | Announcement |
|---|---|---|---|
| **idle** | `[ Sync roles ]` enabled, `RefreshCw` icon | "Roles synced {relative}" or "Never synced" (`discord_neverSynced`) | — |
| **in flight** | disabled, `Loader2 animate-spin`, label `discord_syncing` — "Syncing…" / "Synchronizuji…" | — | `role='status' aria-live='polite'`: "Syncing Discord roles" |
| **queued** (server accepted, bot hasn't run yet) | disabled, label `discord_syncQueued` — "Queued…" | muted "This usually takes a few seconds." (`discord_syncQueuedHelp`) | polite: same |
| **success** | re-enabled after cooldown, icon flips to `Check` for 2 s | see result copy below | polite |
| **failure** | re-enabled, `variant='outline'` unchanged | inline `Alert variant='destructive'` under the row | `role='alert'` (assertive) |

**Cooldown:** after any completed run the button is `disabled` for 60 s with the
label `discord_syncCooldown` — "Sync again in {seconds}s". This is not
decoration: without it, a frustrated user hammering the button generates a
Discord rate-limit storm for the whole guild, which degrades every other team on
the same bot token. Hold the countdown timer in a `useRef` and clear it on
unmount (`AGENTS.md` § clipboard/timer rules).

**Success result copy — be specific, not "Done":**

| Outcome | Key | English | Czech |
|---|---|---|---|
| roles changed | `discord_syncSuccess_changed` | "Discord roles updated — {added} added, {removed} removed." | "Role na Discordu aktualizovány — {added} přidáno, {removed} odebráno." |
| nothing to do | `discord_syncSuccess_noop` | "Your Discord roles were already up to date." | "Tvoje role na Discordu už byly aktuální." |
| partial | `discord_syncSuccess_partial` | "{applied} of {total} roles applied. {failed} couldn't be set — see below." | "Nastaveno {applied} z {total} rolí. {failed} se nepodařilo nastavit — viz níže." |

A "Done" toast for an operation whose visible effect is in another application is
useless; the user needs to know *whether anything actually changed* so they can
decide whether to go look in Discord.

**Failure copy — the full set.** Each is a distinct, actionable case; a single
generic error here is the difference between a self-service fix and a support
ticket.

| Error code | Key | English | Czech |
|---|---|---|---|

Ask your captain to move the Sideline bot's role higher in the server's role list." | "Discord nedovolí botovi přidělit roli {role}, protože je v seznamu rolí výš než role bota. `role_hierarchy` and `bot_missing_permission` are the two failures that actually
happen in the field and they are both 100 % captain-fixable — the copy therefore
names the exact Discord setting to change rather than saying "permission error".

**Auto-sync triggers (no button press):** on observed guild join (§4.3), on
Sideline role assignment/removal (existing `role_sync_events` path), and once on
the first dashboard load after `connected` flips. The manual button exists for
when those miss.

### 5.5 Result surface: inline, not toast-only

Use the standard `useRun()` toast (`run({ success: … })`) for the *happy* path,
but **also** render the outcome inline under the button, persistent until the
next sync. A toast is a 4-second ephemeral artefact; a user who looks away
misses it and has no way to find out what happened. The inline line answers
"did that work?" ten minutes later. Failures are inline-only + `role='alert'`
(no auto-dismiss).

## 6. Data contract the UI needs (for the architect)

Design-driven requirements, not an implementation proposal. Everything below is
consumed by the components in §2–§5.

**Per (user, team) connection state** — must be readable at any time, from any
device, without a client-side token:

```
discordConnection: {
  state: 'connected' | 'not_connected' | 'unknown'
  inviteUrl: Option<string>          // current usable discord.gg link, if any
  inviteError: Option<InviteGeneratorErrorCode>
  guildConfigured: boolean           // false → §4.2(b)
  lastRoleSyncAt: Option<Date>
  roleSyncState: 'idle' | 'queued' | 'syncing'
  lastRoleSyncResult: Option<{ added: number; removed: number; failed: number }>
  lastRoleSyncError: Option<{ code: DiscordSyncErrorCode; role?: string }>
}
```

- `state` MUST be tri-state (§3.6). A boolean here reintroduces the lockout risk.
- `inviteUrl` MUST be server-held, not `localStorage`. `localStorage` keeps only
  the snooze timestamp.
- **Regenerate invite** endpoint (§4.2a) — idempotent, rate-limited server-side
  (≤3/hour/user), returns the same shape.
- **Enqueue role sync** endpoint — accepts a `teamMemberId` (self, or any member
  with `role:manage`), returns immediately with `roleSyncState: 'queued'`; the
  UI polls the connection object. Bulk variant takes a `teamId`.
- `DiscordSyncErrorCode` is a closed union matching the table in §5.4 exactly.
  The UI maps code → copy; the raw upstream message is never shown to a player
  (it may be shown to `role:manage` holders behind a `<details>`, following the
  precedent in `.work-plans/discord-native-onboarding-design.md` §3).
- Existing enums to reuse rather than duplicate: `InviteGeneratorErrorCode`
  (`packages/domain/src/models/Onboarding.ts`) for invite generation;
  `RoleSyncEventType` (`packages/domain/src/models/RoleSyncEvent.ts`) already
  models `role_assigned` / `role_unassigned`.

## 8. Accessibility

1. **The interstitial is a route, not a modal** (§2.1) — chosen specifically to
   avoid focus-trap bugs. On mount, move focus to the card heading:
   `<h2 tabIndex={-1} ref={headingRef}>` + `headingRef.current?.focus()` in a
   mount effect, so a screen-reader user landing there after a redirect hears
   the purpose of the page rather than being dropped at document start.
2. **If a modal is ever used instead** (rung 2, §3.5, blocking an inline
   action): it must be always-mounted and `open`-driven per `AGENTS.md`, must
   have `aria-describedby` on the body copy, must return focus to the triggering
   control on close, and must **never** suppress `Escape` — a gate you cannot
   dismiss with the keyboard is an accessibility failure, not extra enforcement.
3. **Async results are announced.** One `<div role='status' aria-live='polite'>`
   per card wraps the sync status line and the connect status line. Failures
   render in a `<div role='alert'>` (assertive) so they interrupt. Never announce
   the same string twice (toast + live region both firing) — the toast carries
   the success, the live region carries the state transition.
4. **Never colour-only.** Every state pairs an icon with text: `connected` =
   `CheckCircle` + `Badge variant='success'` + the word "Connected";
   `not_connected` = `AlertTriangle` + amber + the words. The amber/red palette
   from `OutstandingPaymentsBanner` is reused as-is, including its dark-mode
   variants, so contrast is inherited from an already-shipped pattern.
5. **Icon-only controls need `sr-only` labels** — the copy button on the invite
   URL (`discord_copyLinkAria` — "Copy Discord invite link") and the nav badge
   dot (`discord_navNeedsAttention`), per `AGENTS.md` rule 3 on icon triggers.
6. **The countdown cooldown must not be announced every second.** Render the
   countdown inside `aria-live='off'` / plain text and only announce the
   idle→cooldown and cooldown→idle transitions.
7. **Keyboard order on the interstitial:** heading → primary "Open Discord
   server" → invite URL (selectable) → copy button → "Skip for now". "Skip for
   now" is last but must be reachable and must be a real `<Button>`, never a
   styled `<span>`.
8. **The invite URL is selectable text**, not `user-select: none` decoration —
   screen-magnifier and voice-control users need to read and dictate it.
9. **Mobile:** the interstitial card is `w-full max-w-md` with `px-6`; the
   primary CTA is `w-full` and ≥44 px tall; the dashboard card's CTA stacks below
   the text under `sm:` rather than shrinking to an unreachable tap target.

## 11. Open questions for the architect

1. **Is `is_in_guild` a stored column or derived per request?** The tri-state in
   §3.6 requires "we have never observed this user in this guild" to be
   distinguishable from "we observed them absent". A nullable
   `team_members.discord_guild_joined_at` plus a per-guild
   `guild_members_backfilled_at` satisfies this; a boolean does not.
2. **Does the bot backfill guild members on `Ready`?** Step 1 of §3.6 depends on
   it. If not, the interstitial redirect cannot ship in the same release as the
   card + badge, and should follow one release later.
3. **Where do invite URLs live long-term?** `invite_acceptances.discord_code`
   exists but is single-use and tied to one acceptance. The §4.2a "regenerate"
   affordance needs a supported way to mint a replacement for an already-joined
   team member.
4. **Is `role_hierarchy` distinguishable from `bot_missing_permission`** in the
   Discord error we get back? The copy in §5.4 is materially better if it is;
   if not, merge the two rows and use the `bot_missing_permission` copy with
   both remedies mentioned.
5. **Does `Guild/RegisterMember` get the "already active member" fix** in this
   bug, or is the manual sync button the whole fix? The UX assumes the former;
   if only the button ships, §5.2's "Roles synced {relative}" will read "Never
   synced" for the entire existing user base and the amber card should
   provisionally be shown for members whose `lastRoleSyncAt` is `None`.
